Executive summary

We looked for safe ways to make Compound Engineering faster for a team that runs it many times a day. The maintainer has already captured most of the easy wins in the last two months: a cheap review path for small changes, smaller skill files, parallel work by default, and timing logs for code review. Because of that, most ideas we generated were either already done, already decided against, or not yet provable.

Five ideas survived a strict check against the code, the upstream issue tracker, and our own session history. The best one is a one-sentence fix to a measured problem: code review wastes about ten turns re-reading files because of how it asks the model to read them. The most interesting one came from our own sessions: review agents are told to receive a large, detailed brief, but in practice they get a short paraphrase of it, which costs quality. A small script would fix that and keep the run fast.

The biggest lever we found is not a speed change at all. Only code review can show where its time goes. The maintainer has said several speed changes are waiting on measurement, so a free, read-only timing report for every skill would unlock the next round of speedups. We recommend filing ideas 1, 2 and 3 first.

Grounding Context

Codebase Context

Each core skill is a small SKILL.md plus required-read references (ce-plan about 4,800 reference lines, ce-code-review about 3,400, ce-doc-review about 2,500). ce-code-review already chooses lite, focused or full depth by consequence (references/modes-and-output.md, scripts/review-scope.py), and logs per-stage wall-clock to stages.jsonl through scripts/run-log.py (#1723). No other skill logs stage time, and the skill-eval harness records exit code and byte counts but no duration (tests/skill-eval-cell/run.ts:429-436).

The measured full review in docs/plans/2026-09-15-review-spine-cost-eval-report.md took 1,100s on Claude: select 112s, peer 349s, dispatch 285s, merge 192s. The learning docs/solutions/skill-design/review-cost-is-in-entering-the-spine-not-the-findings.md says spine cost barely depends on diff size, and lists three open follow-ups: reference load and per-turn context growth, per-stage instrumentation beyond code review, and CI workflows as a lens floor.

Past learnings

The maintainer measures before optimizing, removes before adding, gates by consequence rather than size, and requires a serial fallback on every host. #1815 (merged 2026-10-01) kept ce-doc-review's reviewer lenses as independent subagents and named two gates that "wait until they're measured".

External context

Prior art on prefix caching for subagent fan-out (claude-code #74318, cost only), incremental re-review (Cursor Bugbot), early-stop voting (EMS), risk-gated review funnels (Meta RADAR) and fast lanes in spec frameworks (BMAD, Kiro).

Our own sessions

Across 4 local Claude Code sessions on CE 3.24.0 to 3.27.0 (last 45 days), we measured 106 reviewer spawn prompts. Code-review prompts had a median of 4,509 bytes (max 9,085). Doc-review prompts had a median of 3,312 bytes (max 4,831). Crude skill durations from the same transcripts could not separate agent time from human idle time, which is itself evidence for idea 3.

1. One Read call per reference at the code-review Stage 4 pointer

Idea 1Axis: Per-turn context weightConfidence: 85%Complexity: Low
Description
At the Stage 4 read pointer (skills/ce-code-review/references/dispatch-reviewers.md:61), replace "read them ... in one parallel read-tool wave" with: issue one file-read call per reference, all in the same message, and never join files in a shell cat. Pin it with a tool-trace assertion in the existing live review cell (each Stage 4 reference read at most once, no multi-file shell read).
Basis
direct: the maintainer's own eval, docs/plans/2026-09-15-review-spine-cost-eval-report.md:35: "turns 24 to 35 are twelve turns for what the plan expected to be two reads. The headless Claude orchestrator concatenated several large files into one cat call, the tool result was truncated, and it re-read the truncated tail and then the individual files ... The baseline run showed the same pattern ... the fix would be one reference per read call at the Stage 4 pointer. Not changed in this PR; recorded as follow-up." No upstream issue tracks it (#1412 and #1497 are a different truncation).
Rationale
Every orchestrator turn on the full path re-reads roughly 180k tokens of context (12.5M cache-read over 68 turns), so about ten wasted turns cost about 1-2 minutes and about 1.8M cache-read tokens per full Claude review. It happened in both the baseline and the post-#1723 run, so it is systematic rather than a fluke.
Downsides
Savings are Claude-specific (Codex used 29 tool calls and did not show it). The minute estimate uses the run's average turn time, so the issue should state 1-2 minutes, not a precise figure. Findings are unaffected because the same files are read.

2. Render reviewer prompts to files by script, spawn with a short pointer

Idea 2Axis: Per-turn context weightConfidence: 60%Complexity: Medium
Description
Both review skills tell the orchestrator to assemble each reviewer's prompt by inlining the full persona file, the shared template, scope rules and the JSON schema. ce-code-review's template block alone is 12,525 bytes, before a 5-10 KB persona, 4,954 bytes of diff-scope rules and the 8,192-byte schema. Orchestrators in real sessions do not do this. They send a paraphrase of a few KB. Proposal: a small stdlib script (beside run-log.py) writes each fully assembled prompt to <run-dir>/prompts/<reviewer>.md. The spawn prompt becomes a short pointer: read this file first, then review. The orchestrator no longer needs to read persona files into its own context at all.
Basis
direct: skills/ce-code-review/references/dispatch-reviewers.md:63-67 ("Each persona subagent receives: 1. Their persona file content ... 2. Shared diff-scope rules ... 3. The JSON output contract") and skills/ce-doc-review/references/dispatch.md:9 ("pass its full content as {persona_file}"). direct: our measurement of 106 real spawn prompts on CE 3.24.0-3.27.0: code median 4,509 bytes, doc median 3,312 bytes, versus roughly 32-36 KB specified for code review. In the six code prompts we inspected, none carried the template's calibration paragraph and none pointed the reviewer at its persona file. direct: docs/solutions/skill-design/pass-paths-not-content-to-subagents.md (the maintainer's own path-passing learning).
Rationale
Two problems become one fix. Quality: reviewers appear to run on a compressed brief, so the persona's failure modes, suppress conditions and calibration may never reach them. Speed: following the spec literally would make the orchestrator generate roughly 8-9k output tokens per reviewer, which is the slowest kind of token. A script makes the faithful path the cheap path. It also removes the persona and template reads from the orchestrator's context, which rides along on every later turn (the learning's open "per-turn context growth" follow-up).
Downsides
Our evidence is one user's Claude Code sessions (4 sessions), so the maintainer should confirm with his own transcripts or the eval harness. A reviewer could skip reading the file. A cheap guard is to have the script stamp a nonce that the reviewer echoes in its artifact, checked by the existing findings helper. Hosts without file access keep today's inline path.

3. A read-only session profiler that times every CE skill

Idea 3Axis: Seeing where time goesConfidence: 70%Complexity: Low-Medium
Description
Add a committed script that reads a host session transcript and prints, per CE skill invocation: wall-clock by phase, assistant turns, cache-read tokens, the longest tool waits, human think-time separated out, and files read more than once. Build it on the transcript parsers ce-compound already ships (skills/ce-compound/scripts/session-history/extract-metadata.py, extract-skeleton.py, which handle Claude, Codex, Cursor and Pi). Optionally, add duration_ms to each skill-eval cell record as a report-only column.
Basis
direct: only ce-code-review has stage timing; tests/skill-eval-cell/run.ts:429-436 records no duration; the #1723 plan deferred a cross-run consumer because "nothing consumes it yet". direct: #1815: "Two possible gates wait until they're measured: re-running only the affected ce-doc-review reviewers in round 2, and running ce-simplify-code inline on small scopes." direct: idea 1's defect was found only by hand-grading a tool trace.
Rationale
This is the "observe" step of the loop. It costs zero turns at runtime, which avoids the main objection to adding run-log.py calls to lfg (lfg's step boundaries are skill invocations, not shell calls, so each log call would be an extra turn at full context). It unblocks the maintainer's own deferred gates and turns the "hold" ideas below into decisions.
Downsides
No direct speedup. Transcript formats drift across host versions, so the parser should fail soft and be pinned with a fixture per host. Codex exposes less per-subagent usage, so some columns will be Claude-only.

4. lfg: run the browser test after push, while CI runs

Idea 4Axis: Handoffs and pauses between stepsConfidence: 65%Complexity: Low
Description
lfg runs ce-test-browser (step 8) before ce-commit-push-pr (step 9), yet nothing consumes its result. Reorder to push first, then run the browser test while remote CI and review bots work, then babysit. The browser test must still finish before DONE, and a failure goes into the PR (comment or body) and the DONE report, not only a log line. A narrow companion change: ce-test-browser should state an explicit Skip exit when no changed file maps to a route, before it selects a driver.
Basis
direct: grep -rn -i browser skills/lfg/ returns two lines only: SKILL.md:47 (do not run browser tests while fixes are uncommitted) and SKILL.md:53 ("Invoke the ce-test-browser skill with mode:pipeline"). skills/ce-test-browser/SKILL.md:44-45: "Pipeline mode does not pause" and "Pipeline mode does not ask - log the failure and continue." skills/lfg/references/shipping.md:33 already runs babysit unconditionally, so CI wait time is spent anyway.
Rationale
Steps 7 to 10 are strictly serial and CI is pure waiting. The browser test is the one stage that is independent of the commit and does not gate it, so overlapping it with CI saves about min(browser test, CI) on every UI-touching lfg run, with no loss of checking.
Downsides
A browser failure is reported after the PR is open rather than before. Stack mode (shipping.md:19-25) hands babysit off from step 9, so the reorder must respect that branch. Saving is unmeasured and zero for non-UI runs.

5. Start the code-review peer after Stage 2 when its trigger is already certain

Idea 5Axis: Subagent fan-out and waitsConfidence: 45%Complexity: Low
Description
The cross-model peer is the slowest leg of a full review, but it starts at Stage 3d, after reviewer selection. When the scope helper's own count already meets the adversarial trigger (at least 50 changed code lines), start the detached peer at the end of Stage 2 and do selection while it runs. Every other case keeps today's timing, including the judgment triggers (auth, persistence, retries), depth:full and apply authority. The disclosure and route checks move with the start, along with the rule that removes the in-process adversarial reviewer from the roster.
Basis
direct: skills/ce-code-review/references/cross-model-review.md:89 ("At Stage 3d (routing), start it as a detached, supervised job ... Only after that call returns may the host finalize the local reviewer roster"). skills/ce-code-review/references/persona-catalog.md:38 (adversarial: ">=50 changed code lines; ..."). Eval report stage table, lines 42-44: select 112s, peer 349s, dispatch 285s.
Rationale
In the measured run the peer finished about 64 seconds after local dispatch, so it sat on the critical path. Starting it earlier is the only way to shorten that path without changing any reviewer's work, and it costs no extra tokens when the trigger is certain.
Downsides
The saving is capped by the peer-minus-dispatch gap (64s in one sample) and is zero when local dispatch is slower. The maintainer can check this cheaply first, because stages.jsonl already exists for every code review. Moving the start also means code leaves the machine slightly earlier, so it is only safe on the mechanical trigger.
